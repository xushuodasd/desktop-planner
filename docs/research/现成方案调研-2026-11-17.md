## 二、结论

**没有现成软件能同时满足 R-a~R-e 五条硬条件；结论为「部分满足需改造」，且数据模型（计划/已办 + 本地 JSON 供 AI 读写）决定了自研是必要的。**

分项判断依据（与上表一致）：

1. **R-c（本地 JSON 给 AI 读写）是全行业盲区**：所有现成软件要么云同步强制登录（To Do、TickTick），要么私有格式不公开（小智桌面、360桌面助手、8GadgetPack、Sticky Notes），唯一数据开放的开源路线（Rainmeter 皮肤、ApexTodo）用的是 ini/Markdown 而非 JSON。
2. **R-a（悬浮图标+点击展开半透明面板）形态接近但交互不匹配**：现成工具都是"常驻面板/挂件"或"全局快捷键唤出"，没有"小图标常驻 + 点击展开半透明面板"的组合；该交互需自定义实现。
3. **R-b（计划/已办双区逐行）无现成实现**：现成 todo 均为通用清单模型，无人按"时间段计划 + 已办流水"的数据结构设计。
4. **开源项目提供了最接近的技术参考**：BUG-gao/floating-todo（Tauri，常驻/半透明/置顶悬浮待办，描述与需求几乎逐字一致）、XGxin/ApexTodo（本地 Markdown 待办挂件）、alanfloyd-dev/desktop-todo-widget（Tauri local-first）、widget-js/widgets（740★ Windows 桌面小组件框架）证明了该形态可低成本实现，但均未完整覆盖需求，且多数许可证缺失或星数较低。

## 四、技术路线建议（供总监决策，本报告不做决定）

| 路线 | 形态 | 优势 | 劣势 / 前置条件 |
|---|---|---|---|
| A. Tauri 2 + Web 前端（Rust 后端） | 参考现成开源：BUG-gao/floating-todo、alanfloyd-dev/desktop-todo-widget 均为此栈 | 包体小、内存占用低（贴合"轻量"）；无边框/透明/置顶窗口能力成熟；JSON 读写完全自主；可借鉴上述两个 MIT/小项目的窗口实现思路 | 本机无 cargo/Rust，需新增工具链（rustup）；团队需 Rust 能力；**cargo/pnpm 安装依赖受网络直连失败影响，需先解决** |
| B. Electron + Web 前端（纯 JS 栈） | 参考现成开源：EasonGuuu/Deskweek、chenwy777/pebble-todo 为此栈 | 本机 Node v24.20.0 + git 已就绪，团队上手最快；透明置顶窗口与 JSON 读写同样成熟；pebble-todo 已带 MCP/AI 集成思路可参考 | 包体大（100MB+）、内存占用高，与"轻量好看"诉求有张力；同样需先解决 npm 直连/镜像问题 |
| C. Python 3.12 + pywebview（或 PySide6） | Python 系桌面窗口方案 | Python 3.12.10 已就绪；JSON 处理与 AI 联动天然同栈（后续 AI 程序读写数据零成本）；pywebview 支持透明置顶窗，UI 可用 Web 技术实现 | PyInstaller 未安装（打包需装）；纯 Python 桌面 UI 精美度与 Win11 原生风格实现成本高于 Web 前端；pip 直连网络本次测试失败，需先验证 |

**三条路线共同的前置风险**：pypi.org / registry.npmjs.org / github.com 直连 HEAD 全部失败（相同"接收时发生错误"），任何路线开工前应先解决包管理网络（配置镜像源或代理），否则依赖安装会阻塞。

**给决策的两条参考线索**（非结论）：
- 若优先"轻量 + 数据模型自控"，开源社区已用 Tauri 验证了该形态的最小成本路径（路线 A），且 BUG-gao/floating-todo 的实现可作为参考底板（注意其无许可证，不能直接复用代码，只能参考设计）。
- 若优先"团队当前栈最快交付"，路线 B/C 依赖本机已就绪的环境；但无论哪条路线，"计划/已办 + JSON"的数据模型都需要自研实现，现成软件无一提供。
